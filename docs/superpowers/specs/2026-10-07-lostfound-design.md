## 0. 摘要

为学校 L&F（失物招领）角落设计的**真实落地系统**：一台锁定的 iPad 跑 PWA 作为现场操作台，配合编号投递柜与二维码引导牌；师生用自己手机扫码打开网页完成登记与认领。核心闭环「捡到 → 登记 → 现场确认入库（动态分配格位）→ 公示 → 冷冻期与核验 → 认领 → 核销出库 → 积分发放」，以**动态格位 + 非公开特征核验 + 冷冻期 + 延时发放 + 全程留痕**抑制刷分、抢领与冒领。中英双语，视觉与学校在线门户同源。

## 1. 背景与目标

**现状痛点**：失物堆放无人管理、找回靠翻堆、登记打字慢造成排队、无激励机制、存在「自导自演刷积分」的隐患。

**设计目标**（成功标准）：

1. 每件物品从进门到出门都有系统记录，可追溯（谁登记、谁认领、何时出库）。
2. 捡到者登记全程 ≤ 2 分钟、不打长字；失主认领路径 ≤ 3 步。
3. 积分只能通过「物品被真实认领」获得，刷分在经济学与规则上均不划算。
4. G6-8（无手机）与 G9+（有手机）都能顺畅完成全流程。
5. 看起来像「学校官方做的」—— 门户同源配色、克制、无 AI 生成感。

**明确不做**（YAGNI）：微信小程序、电子锁柜、人脸识别、多校区、家长通知。

## 2. 用户与角色

| 角色 | 说明 | 使用端 |
|---|---|---|
| 捡到者（G9+，有手机） | 扫码登记、获积分 | 手机网页 + iPad 确认 |
| 捡到者（G6-8，无手机） | iPad 直办登记 | iPad PWA |
| 失主 | 浏览公示、申请认领、取回 | 手机网页 或 iPad 直办 |
| 管理员 | 复核高价值认领、处理异常、发兑换、看数据 | 隐藏后台 /admin（桌面优先） |
| 所有学生 | 查积分、逛积分商城 | 手机网页 / iPad |

**硬性场景约束**：G6-8 年级学生不能用手机 —— 一切流程必须有 iPad 直办路径；iPad 是公共屏幕，空闲态只显示公开信息。

## 4. 核心闭环流程（双路径）

### 4.1 路径一 · 手机路径（G9+ 及所有有手机者）

1. **扫码登记**：扫投递柜上的引导二维码 → 网页登记（拍照 + 非公开核验特征、描述、拾获地点、类别、本人学号+姓名+班级；价值档由类别自动判定，登记人不可改）。
2. **获得投递凭证**：系统**只**生成 6 位投递凭证码，**不预分配格号** —— 以票据样式显示在手机上（15 分钟倒计时）。
3. **iPad 确认入库 · 动态分配格位**：在 iPad 扫/输凭证码 → 系统**此时**才把一个当前空闲格号原子地分配给该物品 → 大屏显示「请放入 N 号格」→ 放入并点「已放入」→「已入库 ✅」。**凭证码 15 分钟内未确认即自动作废**，释放占位、防止占格与错放。
4. **自动公示**：物品进入公示列表 —— 照片+描述+地点+时间公开，**但「非公开核验特征」不公开**（仅用于认领核验，见 §6）；捡到者只显示**姓名+班级**（学号永不公开）。
5. **冷冻期**：入库公示后 1 小时（后台可调 1–2h）为冷冻等待期：期间申请照常受理；冷冻期结束时**仅 1 人申请且核验通过 → 自动通过**；**≥2 人申请 → 全部转人工复核**。
6. **申请认领**：失主在列表找到物品 → 填学号+姓名+**核验特征答案** → 通过核验与冷冻期后生成**限时领取码**（默认 48h 有效，可后台调整）。
7. **iPad 核销出库**：失主在 iPad 输/扫领取码 → 确认出库 + **拍照存证** → 取走物品。
8. **积分发放**：出库完成那一刻，系统自动给捡到者积分（延时发放）。

### 4.2 路径二 · iPad 直办（G6-8 及所有无手机者）

- **登记 = 入库，一步完成**：iPad 点「我捡到了东西」→ iPad 拍照 + 补一个非公开核验特征（点选式问题，见 §6）→ 点选标签（类别/地点，价值自动判定，全程不打字）→ 填学号+姓名+班级 → 系统动态分配当前空闲格号 → 大字显示「请放入 N 号格」→ 点「我已放入」→ 入库完成。直办路径天然无凭证码与占位窗口。
- **认领 = 核验 + 出库，一步完成**：iPad 点「我要找物品」→ 浏览公示 → 选物品 → 答**非公开特征问题** → 答案匹配即视为强核验（本人在场 + 知道非公开特征），当场确认出库 + 拍照存证、取走；答案不匹配、无核验特征或高价值物品 → 转人工复核；冷冻期内该物品已有 ≥2 人申请 → 同样转人工复核。
- **兑换**：iPad 上以学号+姓名查询积分、发起兑换 → 生成「待发放订单」，管理员定期发实物。

### 4.3 两路径一致性

两条路径写同一个数据库，公示、积分、后台、审计完全一致，不存在两套账。

## 5. 身份、积分与防作弊

### 5.1 身份与账号

- **学号 = 唯一账号**（7 位数字，如 9031622）。登记/认领/兑换时填学号+姓名+班级；学号格式校验（7 位数字）+ 二次确认。
- 对外公示与任何公开 API **永不返回学号**；捡到者对外仅显示姓名+班级；**认领人（失主）不在任何公开位置显示**，仅管理员可见。
- **积分查询分级**：仅凭学号 → 只显示**总积分**与**贡献次数**；积分明细、物品历史、兑换订单属敏感数据，须二次校验 —— 学号 + 完整姓名精确匹配，或预留 4 位 PIN（积分页首次使用时可设置，仅存哈希）。

### 5.2 积分规则（数值可在后台调整）

| 事件 | 积分 | 说明 |
|---|---|---|
| 物品被成功领取（出库完成） | 捡到者 +10 | 延时发放：登记不发分，认领成功才结算 |
| 高价值物品被领取 | 捡到者 +25 | 钱包/手机/平板/耳机/证件类 |
| 失主感谢打赏 | 1–10 分 | **三限**：仅限已完成的真实出库认领单、每单限一次、计入接收者月上限（见 §5.3-7） |
| 登记但无人认领 | 0 分 | 只计入「贡献次数」展示，防滥登记刷分 |
| 兑换 | -对应分值 | 生成待发放订单 |
| 每人每月上限 | 100 分 | 超出后当月不再累加（含打赏所得），后台可调 |

### 5.3 防作弊防线（七层）

> 前提：公示信息近乎全透明 —— 唯独每件物品保留一个**非公开核验特征**。防线如下。

1. **非公开特征核验**：登记时强制采集一个不公开的核验特征（捡到者对模板问题作答，如「内侧的字/夹层物品」，可另拍一张不公开细节照）；失主认领必须答对（模糊匹配）才触发自动通过 —— 信息不对称杜绝「照着公示冒领」。
2. **冷冻期**：入库公示后 1 小时（可调 1–2h）冷冻等待期，期间多人申请自动转人工复核，杜绝「秒抢冒领」。
3. **分级核验**：高价值物品一律人工复核；捡到者无法作答（无核验特征）的物品一律人工复核。
4. **出库留痕**：每次核销 iPad 拍照存证 + 认领人学号入档，冒领可追责、纠纷可回溯。
5. **异常自动标记**：登记后 10 分钟内被认领（秒领）、同一认领人反复出现（≥3 次/月）、同一对登记/认领配对过频（≥2 次/月）、相似描述重复登记、冷冻期内同物多人申请 → 自动黄标，进管理员抽查队列。（阈值可后台调整。）
6. **经济学防线**：奖品定价使「扔一件真物品换积分」永远亏损（积分价值远低于物品价值）。
7. **规则防线**：延时发放 + 月度上限（含打赏所得）+ 登记不加分 + **打赏三限**（绑定已出库认领单、每单一次、计入接收者上限）。

## 6. 认领核验（非公开特征 + 冷冻期 + 分级）

**登记时（捡到者）**：系统从模板题库给出 1 道必答「非公开特征」问题（如「物品内侧/夹层有什么字或图案？」「里面装着什么？」），答案**不公开**、仅供核验；可另拍一张不公开细节照供人工复核。确实无法作答时可选「无法描述」→ 该物品认领一律走人工复核。

**认领时（失主）**：回答同一问题 → 系统归一化后模糊匹配（去空格/大小写/标点，相似度阈值后台可调）→

| 场景 | 结果 |
|---|---|
| 答案匹配 + 冷冻期结束且无竞争 | 自动通过，发限时领取码（默认 48h） |
| 答案不匹配 / 留空 | 转人工复核（不直接拒绝，防误伤） |
| 冷冻期内 ≥2 人申请 | 全部转人工复核，管理员裁定 |
| 高价值物品 | 一律人工复核 |
| 物品无核验特征 | 一律人工复核 |

- 人工复核通过后才生成领取码；领取码过期未使用 → 物品回到「待认领」，可再次申请。
- 认领被拒（复核不通过）→ 记录原因，物品重新公示。

## 7. 积分商城与兑换

- 商城在网站与 iPad 端均可浏览；兑换 = 扣分（乐观锁保护，见 §10）+ 生成「待发放订单」。
- 管理员按订单定期发放实物并标记完成；库存不足自动下架。
- 首批奖品池（示例，由管理团队实际运营）：文具套装 40 分、打印额度 20 页 25 分、小卖部 5 元券 50 分。

## 8. 视觉设计系统

**路线**：hallmark custom（学校色锚定）· 风格族 modern-minimal · 基调 utilitarian + 校园归属。
**受众/任务/基调**（推断已披露并确认）：全校师生 G6-12+员工；手机端=登记/公示/认领，iPad=现场直办核销；官方工具感、像「学校官方做的」。

### 8.2 字体

- 正文/界面：**Lato**（Latin，自托管 400/700/800，与学校门户同源）+ **PingFang SC / Noto Sans SC**（中文系统栈）
- 数字/编码：**IBM Plex Mono**（自托管 400/600/700）—— 格号、凭证码、领取码、学号、时间戳、统计数字一律 mono
- 纪律：标题不斜体；字阶 12/13/15/17/22/28；正文 ≥14px（移动端 15px 基准）

### 8.3 签名元素 —— 「格位牌 & 认领券」

- **格位牌**：物品卡上的 mono 大号格号标签（像柜子上的号码牌），列表/详情/出库全程一致。
- **认领券 / 投递凭证**：领取码与投递凭证码渲染为带撕边打孔的票据（虚线 + 两侧打孔圆 + 大号 mono 编码 + 有效期/倒计时），是整个产品被记住的元素。
- 空状态/成功态文案遵循「指路不抒情」：错误不道歉、空屏即邀请。

### 8.4 反 AI 味纪律（hard gates）

不编造数据/评价；不重绘浏览器/手机壳 chrome；所有颜色与字体走命名 token；标题不用斜体；单屏只做一个编排动效；尊重 prefers-reduced-motion；焦点态一等公民；文案用动词具体说事（「保存更改」而非「提交」）。

## 9. 界面结构与响应式

### 9.1 手机端屏幕（375 基准，底部 Tab：公示 / ＋登记 / 我的积分）

1. **公示首页**：顶栏（logo + 中/EN + 积分入口）→ 本周统计条（mono 数字）→ 搜索 + 类别筛选 chips（带彩色圆点）→ 物品卡列表（照片、标题、地点时间、格位牌、状态 chip、捡到者姓名+班级）
2. **登记拾获**：三步（拍照 + 非公开特征 → 描述/类别/地点 → 学号+姓名+班级确认）→ 成功页 = **投递凭证票据**（6 位凭证码 + 15 分钟倒计时 + 「到 iPad 扫码确认入库」指引；格号在现场确认时才动态分配）
3. **认领申请**：物品详情（公开细节）→ 核验特征答案 + 学号姓名 → 通过核验与冷冻期后出**认领券**（领取码 + 有效期）
4. **我的积分**：学号查询 → 总积分 + 贡献次数（公开级）；二次校验后 → 明细流水 + 兑换记录；积分商城（兑换 → 待发放订单提示）

### 9.2 iPad 端状态机（横屏优先，PWA 全屏）

```
空闲屏（深藏青，公开信息only）
├─ 我捡到了东西 → 拍照+非公开特征 → 点选标签 → 学号姓名 → 动态分配格号大字指引 → 「我已放入」→ 入库完成
├─ 我要找物品 → 浏览公示 → 选物品 → 答非公开特征 →
│    ├─ 匹配且无竞争：确认出库 + 拍照存证 → 完成
│    └─ 不匹配 / 无特征 / 高价值 / 多人竞争：转人工复核提示（附领取码输入入口，复核通过后可核销）
├─ 扫码/输码 · 投递确认（手机路径）→ 动态分配格号 → 大字指引 → 入库完成
├─ 扫码/输码 · 核销出库（领取码 6 格大键盘 + 扫码 + 认领信息确认卡 + 拍照存证）
└─ 兑换直办（学号+姓名 → 余额 → 选奖品 → 待发放订单凭证）
```

- 空闲屏组成：顶栏（logo、连接状态、时钟、中/EN）+ 两大动作卡（利用横宽）+ 右侧「今日动态」归还播报 + 底部致谢条。

### 9.3 响应式与大屏适配（硬性要求）

- 断点：**320 / 375 / 414 / 768 / 1024 / 1194 / 1366** 全部人工截图验证；无横向滚动；双行可点文字禁止。
- kiosk：横屏优先（834×1194 目标，左侧动作/输入、右侧信息确认的分栏）；竖屏降级可用。
- 网站桌面（≥1024）：公示列表变 3 列网格 + 右侧「我的积分 / 商城」侧栏。
- 后台：桌面优先，最小支持 1024。

## 10. 技术架构

- **托管**：Cloudflare Workers（API + 静态资产，wrangler 单仓库部署），D1 SQLite 存储 —— 与既有项目同架构，零成本、自带 HTTPS/CDN。
- **前端**：原生 HTML/CSS/JS（无框架），CSS 命名 token（生产 OKLCH）；PWA = manifest + Service Worker（静态壳离线缓存，断网时 kiosk 显示「网络不可用，请稍后重试」）。
- **离线高可用**：照片 Blob、登记草稿与本地队列一律存 **IndexedDB**（明确弃用 5MB 限额的 localStorage，避免存证照片把存储撑爆）；补发优先 Background Sync，iOS 等不支持的环境退化为 `online` / `visibilitychange` 事件触发静默补发。
- **二维码扫描**：jsQR/ZXing **本地打包**（不经 CDN），iPad 摄像头权限首次授予；所有扫码入口都有**手动输码兜底**。
- **图片安全**：前端一律 **Canvas 重绘导出**（顺带压缩至 ≤1600px、JPEG ≤1MB），从源头抹除 GPS / 设备型号等 Exif 元数据；后端校验 **Magic Byte**（JPEG `FF D8 FF` / PNG `89 50 4E 47`）与体积 ≤1MB，拒绝伪装文件。
- **并发控制（乐观锁）**：所有状态跃迁使用带条件的原子 UPDATE 并严格校验受影响行数 `changes == 1`，失败返回 409「已被处理」并刷新前端状态。统一模式：
  ```sql
  UPDATE items SET status='returned' WHERE id=? AND status='ready';
  ```
  应用于：核销出库、格位动态分配（`UPDATE items SET slot_no=? WHERE id=? AND slot_no IS NULL` + 格号空闲校验）、兑换扣分、打赏一次性（`claims` 上打赏唯一约束）。
- **API 草案**：

| 端点 | 方法 | 说明 |
|---|---|---|
| /api/items | GET | 公示列表（公开字段不含学号与核验特征） |
| /api/items/:id | GET | 物品详情（同上白名单） |
| /api/report | POST | 登记拾获（multipart 照片+字段）→ 返回**投递凭证码**（15 分钟有效，不分配格号） |
| /api/kiosk/confirm-drop | POST | iPad 投递确认（凭证码）→ 原子分配空闲格号 → 入库 |
| /api/claims | POST | 认领申请（含核验答案）→ 自动通过/进复核/冷冻期等待 |
| /api/kiosk/verify-pickup | POST | 领取码校验 → 认领信息 |
| /api/kiosk/fulfill | POST | 确认出库（存证照片，乐观锁）→ 触发积分结算 |
| /api/points/:student_id | GET | 学号 → 总积分+贡献次数；带二次校验（姓名/PIN）→ 明细 |
| /api/tips | POST | 打赏（绑定已完成认领单，每单一次，计入月上限） |
| /api/rewards · /api/redemptions | GET/POST | 商城与兑换（扣分乐观锁保护） |
| /api/admin/* | 全部 | 口令 + X-Admin-Token：复核队列、黄标抽查、积分调整、兑换发放、过期处理、看板 |

- **数据模型（核心表）**：`identities`(student_id PK, name, class, pin_hash?) · `items`(code LF-YYYY-NNNN, title, desc, category, location, photo, detail_photo?, verify_q?, verify_a?, value_tier, slot_no?(确认入库时才写入), drop_code, drop_code_expires_at, status, registered_by, via, timestamps) · `claims`(item, claimant, verify_answer, status, pickup_code, expiry, evidence_photo) · `points_ledger`(student, delta, reason, ref, month_key) · `tips`(claim_id UNIQUE) · `rewards` · `redemptions` · `risk_flags`(subject, reason, resolved) · `admin_audit`(action, target, at)。
- **物品状态机**：registered（凭证有效，15 分钟窗口）→ in_stock（已入库/公示中，冷冻期 1h）→ claim_pending（认领中/复核）→ ready（待领取，持有有效领取码）→ returned（已归还）｜ registered 超时 → voided（凭证作废释放）｜ in_stock 长期无人认领 → expired（学期末捐赠）。
- **安全**：学号不出公开 API；核验特征与细节照不出公开 API；积分明细需二次校验（§5.1）；速率限制（同 IP/同学号每日登记上限）；后台口令 + token，全部操作写审计；错误信息不泄露内部细节。

## 13. 边界与错误处理

| 场景 | 处理 |
|---|---|
| 断网 | kiosk 显示离线横幅；登记草稿与照片存 IndexedDB，恢复后静默补发 |
| 凭证码 15 分钟未确认 | 自动作废并释放；重新登记即可（旧码不可用） |
| 确认入库时格子已满 | 提示「投递柜已满」，凭证码保持有效至 15 分钟时限，有空格后回 iPad 重扫；大件/特殊情况贴条联系管理员；后台可增格 |
| 冷冻期内多人申请 | 全部转人工复核，管理员裁定通过其一，其余记录原因 |
| 领取码过期 | 物品回到「待认领」，可重新申请 |
| 认领纠纷 | 出库记录（学号+照片+时间）作为凭据，管理员调解 |
| 高价值复核超时 | 队列置顶提醒；管理员不在线时物品保持 in_stock |
| 学号输错 | 格式校验 + 姓名/班级交叉展示确认 |
| 照片上传失败 | Canvas 压缩重试；失败可跳过但物品标记「无照片」并提示补拍 |
| 并发重复操作 | 乐观锁拦截，返回 409 并刷新状态（不会双扣分/双出库） |

## 14. 测试策略

- 核心逻辑 `node --test`：码生成/校验与 15 分钟过期、状态机流转、核验模糊匹配、积分结算与月上限（含打赏）、防刷标记、API 字段白名单（学号/核验特征不外泄）。
- 并发测试：乐观锁路径（重复核销 / 并发认领 / 同格争用 / 重复打赏）必须 409 且状态一致。
- 上传安全测试：带 Exif 图片经前端导出后无 GPS 元数据；伪造扩展名、伪装 Magic Byte、超 1MB 文件被后端拒绝。
- 离线测试：IndexedDB 队列断网补发成功；iOS 无 Background Sync 的降级路径可用。
- 浏览器断点验证：7 断点截图逐个过（含 kiosk 横屏）。
- 流程冒烟：手机路径 + iPad 直办路径双全流程；断网恢复路径。
- 验收前 slop 自检：token 覆盖率、真实文案、无占位假数据。
